> RULES — the conventions that make this file load-bearing
>
> 1. **One entry per line, fixed format.** Gates and tests presence-check IDs in this
>    file; prose elsewhere (chat, PR descriptions, commit messages) unlocks NOTHING.
>
> 2. **Entry types:**
>    - `DEC-00x` — a CONFIRM-FIRST decision from charter §5 is confirmed (or overridden).
>    - `RB-xxx`  — a process/re-baseline decision: PR batch authorizations, scope
>      corrections, policy amendments. Number sequentially, never reuse.
>    - `RB-xxxa` — an EXECUTION RECORD under a prior decision, not a new decision. Say so
>      explicitly in the entry text.
>    - `G-x` — human gates (operator executed a [HUMAN] task, sign-off given).
>
> 3. **Namespace rule (design D7).** This file owns `DEC-`/`RB-`/`G-` IDs only. ADR-style
>    rationale documents keep their `D-nn` ids under `docs/decisions/` (e.g. `D-000/D-05`)
>    and plan.md keeps `D-01…D-05`; the prefixes are disjoint, so an ID is unambiguous.
>    A log line decides; an ADR explains.
>
> 4. **Decide, then execute.** A decision is logged as its own line; the PR that executes
>    it is separately costed and cites the line.
>
> 5. **State what an entry does NOT do.** If a decision doesn't unlock gated work, end
>    the entry with it.
>
> 6. **Authorization ordering.** Owner approval given in-session BEFORE work starts may
>    be logged after, landing with the commits it authorizes — but the entry must say so.
>
> 7. **Never spoof a gate.** A transmission/progress record related to a gate must NOT
>    carry the gate's ID.
