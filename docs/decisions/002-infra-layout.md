## D-01 — Terraform layout: one stage subdirectory per D-000/D-06 apply boundary, one `.tf` file per Helm release/CR — not one file per task

`plan.md`'s Project Structure block lists `infra/terraform/` as a flat directory with an inline comment naming components (`# helm releases: airflow, argo, mlflow, lakefs, seaweedfs, cnpg, kube-prometheus`). Read literally as "one file per component, no subdirectories," this collides with D-000/D-06, which is explicit that CRD-installing charts require **a separate apply**, not merely a later resource in the same apply: `kubernetes_manifest` validates against the live API server at plan time, so a CR referencing a CRD from the same `terraform apply` run fails even with `depends_on` set correctly. HashiCorp's own guidance for exactly this CRD-then-CR ordering problem is a genuinely separate Terraform configuration (separate directory, separate state) rather than `-target` — `-target` is documented as an exceptional/break-glass mechanism, not a routine bring-up tool, and a project this deliberate about "one documented command path" (Constitution IV) should not build its Phase 0 bring-up around it.

**Decided:** `infra/terraform/` gets four subdirectories, named after D-000/D-06's own stage prose verbatim (already-established names, not invented here): `00-crds/`, `10-storage/`, `20-platform/`, `30-observability/`. Each is an **independent Terraform root module** — its own state, its own provider configuration (D-03). Within each stage directory, one `.tf` file per Helm release or per Kubernetes CR that Terraform manages directly (`helm_release`, `kubernetes_manifest`, `kubernetes_secret`), named after the release/resource, snake_case — matching the one existing precedent already in `tasks.md`'s own T006 line (`infra/terraform/gpu_operator.tf`, snake_case, single file for a single-chart task).

This resolves the prompt's literal question — does T007 write one combined pair or three separate ones — with neither: **T007 spans three stage directories and at minimum four files**, because CloudNativePG's own D-000/D-06 row splits it internally:

| File | Stage dir | Contains |
|---|---|---|
| `00-crds/cnpg_operator.tf` | `00-crds` | CloudNativePG operator chart (`0.29.0`) — the release that installs the `Cluster` CRD and friends |
| `10-storage/cnpg_cluster.tf` | `10-storage` | CNPG `cluster` chart (`0.8.1`) — the actual `Cluster` CR, which needs the CRD from the file above to already exist |
| `10-storage/seaweedfs.tf` | `10-storage` | SeaweedFS chart (`4.41.0`), no CRDs (D-000/D-06's "No CRDs" list) |
| `20-platform/lakefs.tf` | `20-platform` | lakeFS chart (`1.12.24` — `versions.md` still pins `1.12.22`; stale per D-11's finding below and Follow-up #6), no CRDs |

Whether `plugin-barman-cloud` (`0.7.1`) needs its own file/stage split (it may carry its own CRDs for backup-target objects, which D-000/D-06's table does not address — that table only names "operator CRDs incl. `Cluster`") is **not decided here** — flagged as a T007 follow-up below, since answering it requires checking the plugin chart directly, which is T007's job under its own `WebFetch` provenance rule, not mine to guess.

T010 (Argo Workflows) gets the same treatment for the same reason: D-000/D-06's own stage list names **"Argo controller"** specifically as a `20-platform` occupant, distinct from the CRD stage, so the convention is `00-crds/argo_workflows_crds.tf` + `20-platform/argo_workflows.tf`. The exact Helm mechanism for splitting one chart's CRD templates from its controller templates into two applies (`crds.full` toggled per release, versus a single release with `--set controller.enabled=false` in one and controller-only in the other) is T010's implementation call, not this doc's — this doc fixes only the stage boundary and the file names either mechanism must produce.

T008 (MLflow) and T009 (Airflow): no CRDs (D-000/D-06's "No CRDs" list names both explicitly), one file each, both in `20-platform/`: `20-platform/mlflow.tf`, `20-platform/airflow.tf`.

Agent-permitted local validation (Constitution I / CLAUDE.md's allowed-command list) runs **per stage directory** — `cd infra/terraform/<stage> && terraform fmt -check && terraform init -backend=false && terraform validate` — once per stage directory the dispatch actually wrote into. A dispatch that only touches `10-storage/` and `20-platform/` (e.g. T008, T009) validates only those two; it never needs to touch `00-crds/` or `30-observability/`.

Housekeeping note, not a blocker: `infra/terraform/.gitkeep` (present today, required by `tests/unit/test_repo_structure.py` while the directory is empty — see Verified-correct) becomes vestigial once any stage subdirectory holds real files, since git tracks the file paths that make the parent directory non-empty regardless of the `.gitkeep`. Leaving it in place is harmless; removing it is optional cleanup for whichever of T007-T010 lands first.

## D-02 — `infra/helm-values/` stays flat: one YAML per Helm release, no stage mirroring

Unlike `infra/terraform/`, the values files carry no apply-ordering constraint of their own — a `values.yaml` is inert data read by a `helm_release.values` argument; D-000/D-06's staging concern is about the Terraform *apply graph*, not about where a YAML file sits on disk. Mirroring the stage taxonomy into `infra/helm-values/` would add a second axis of structure for zero benefit and contradicts `plan.md`'s own comment for this directory ("pinned values per chart" — no stage or component-count language at all, unlike the `terraform/` comment).

**Decided:** `infra/helm-values/<release-name>.yaml`, flat, kebab-case, one file per Helm release (matching the same release list as D-01's `.tf` files, i.e. T007 produces `cnpg-operator.yaml`, `cnpg-cluster.yaml`, `seaweedfs.yaml`, `lakefs.yaml`; T010 produces `argo-workflows-crds.yaml` and/or `argo-workflows.yaml` depending on which split mechanism it picks). Kebab-case for `.yaml`, snake_case for `.tf` — again matching the one existing precedent (`gpu-operator.yaml` / `gpu_operator.tf` in T006's own task line), not invented here.

## D-03 — Provider version pins: one `versions.tf` per stage directory, textually identical across all four — first-merged pin wins

Because D-01 makes each stage directory an independent Terraform root module, there is no native Terraform mechanism for one root to inherit `required_providers` from another — each of the four (or, once T006/T046 land, six) root modules must declare its own `terraform { required_providers { ... } }` block. Left undeclared as a shared convention, four independent dispatches will each research and pin a `helm`/`kubernetes` provider version independently and very plausibly land on four different numbers, which is exactly the "internally-consistent, mutually-incompatible artifacts" failure mode this doc exists to prevent — just one level down, at the provider layer instead of the chart layer.

**Decided:**
- Every stage directory gets its own `versions.tf` containing a `terraform` block with `required_providers { helm = { source = "hashicorp/helm", version = "..." }, kubernetes = { source = "hashicorp/kubernetes", version = "..." } }` plus a `required_version` constraint for the Terraform CLI itself.
- Both providers are declared in **every** stage directory that creates `helm_release` or `kubernetes_secret`/`kubernetes_manifest` resources — per D-000/D-09, secrets are bootstrapped via `kubernetes_secret` from operator-supplied `TF_VAR_*`, and that pattern shows up in `10-storage` (SeaweedFS identity secret, D-07) at minimum, so `kubernetes` is not merely `helm`'s dependency here.
- **This doc does not pin the actual version numbers** — that is a literal requiring provenance research (Constitution IV / the infra-scaffolder charter's "resolve the real version WITH PROVENANCE before writing any pin"), which is T007-T010's job, not a convention this doc can supply without fabricating a source.
- **What this doc does fix:** whichever of T007-T010 merges first researches the pin (with the same provenance discipline `versions.md` already requires) and that exact `versions.tf` text becomes canonical. Every subsequent dispatch **copies it verbatim** into its own stage directory's `versions.tf` rather than re-deriving its own — a differing provider-version string across two stage directories should be treated by `spec-guardian` as a blocking finding, the same class of defect as a hardcoded value, since it is exactly the kind of five-artifacts-disagreeing-with-each-other bug this doc exists to prevent.
- Provider **configuration** (not just the version constraint) — `provider "kubernetes" { config_path = var.kubeconfig_path }` / `provider "helm" { kubernetes = { config_path = var.kubeconfig_path } }` (example corrected 2026-08-22 under the RB-007 reconciliation: the original showed the pre-3.x `kubernetes { ... }` *block* syntax, which is schema-invalid against the `hashicorp/helm` 3.x provider the dispatches actually pinned — the correct form is the single nested object attribute, `kubernetes = { ... }`. Flagged by D-005/03 (`docs/decisions/005-t010-argo-workflows.md`) and independently by D-003/05; the dispatches' actual `.tf` files always used the correct 3.x form, so this was a stale prose example only, never a live defect) — reads from a variable, never a literal path, per Constitution III and D-000/D-10 ("terraform runs on the Linux node ... the repo stays parameterized"). `var.kubeconfig_path` is one of the shared variables in D-04's `common.tfvars.example`.

**Process note, stated explicitly rather than left implicit:** "first-merged pin wins" has no mechanism to prevent two of T007-T010 from independently pinning different provider versions *while both are still in flight* — T007-T010 are explicitly parallel `[P]` tasks, so this is a real possibility, not a hypothetical. This doc only guarantees detection (whoever reviews second sees a mismatch and copies the first), via `spec-guardian` treating a mismatch as a blocking finding per the paragraph above — not prevention during concurrent authoring. That is an accepted tradeoff, not an oversight: no cheaper mechanism exists without either serializing the four dispatches (defeating the point of running them in parallel) or introducing a fifth artifact whose only job is holding a shared provider pin before any of the four has researched one.

## D-04 — `*.tfvars.example`: one shared `common.tfvars.example` plus one per stage directory; the `.env.example` boundary

`.env.example` already states the intended relationship: "Terraform consumes the same values via `*.tfvars`, which are also gitignored — the `*.tfvars.example` templates arrive with T006-T010, which own those variables" (plural "templates," implying more than one file, consistent with D-01's per-stage-root design — Terraform only auto-loads `terraform.tfvars`/`*.auto.tfvars` from its **own working directory**, not from a parent, so four independent root modules genuinely need four sets of tfvars, not one).

**The boundary between `.env.example` and `*.tfvars.example`:** a value belongs in `.env.example` if something *other than Terraform* consumes it directly (a runbook step, a shell script, a human reading it for reference). It belongs in a `*.tfvars.example` if it is bound to a `variable "..."` block in a `.tf` file. Host-identity values that both worlds need (`NODE_A_LAN_IP`, `NODE_A_HOSTNAME`, the two GPU UUIDs) legitimately exist as parallel copies in both file formats — Terraform cannot read `.env` directly, and this repo has no tool that reads `.tfvars` into `.env`. This duplication is an accepted cost of the two ecosystems, not a bug; a comment cross-referencing `.env.example` from the tfvars template (and vice versa) is cheap insurance against the two drifting silently.

**Decided, two-tier structure:**
- `infra/terraform/common.tfvars.example` (repo root of the Terraform tree, outside any single stage directory) — cross-cutting, host-level values every stage's `-var-file` invocation needs: `node_a_lan_ip`, `node_a_hostname`, `kubeconfig_path`, and (only for the stage that actually needs them — `20-platform`, where D-01 places `argo_workflows.tf`, the controller/RBAC file; `00-crds` holds only Argo's CRD templates and has no GPU awareness) `orbital_drift_train_gpu_uuid` / `orbital_drift_serve_gpu_uuid`, mirroring `.env.example`'s existing names exactly (Constitution III: don't invent a second name for the same value). Corrected from an earlier draft of this doc that named `00-crds`/`10-storage` here — neither holds any Argo-related file per D-01's own table, and `10-storage` is CNPG-cluster/SeaweedFS territory.
- `infra/terraform/<stage>/terraform.tfvars.example` — component-specific values scoped to that stage's releases: bucket/repo names, storage sizes, the shared secret-name/namespace/cluster-name variables from D-06/D-07, anything that would otherwise be a literal inside a `.tf` file.
- The operator's real `apply` command supplies both: `terraform apply -var-file=../common.tfvars -var-file=terraform.tfvars` (run from inside the stage directory) — this is an operator-run command inside a future `[HUMAN]` runbook (T011/T012), not something this doc or any of T007-T010 executes.
- `.gitignore` needs **no change** for this: its `*.tfvars` / `!*.tfvars.example` patterns carry no leading `/`, so they match at any depth, including inside `infra/terraform/00-crds/terraform.tfvars.example` — confirmed by re-reading the patterns, not assumed (see Verified-correct).

## D-05 — No `.terraform.lock.hcl` will exist after T007-T010, and that is correct — it is a `[HUMAN]` step, not something any dispatch should attempt or silently skip

`plan.md`'s own risk register notes that generating a lock file needs `terraform init` with network access on a Docker-capable host, which no agent has (Principle I: agents never hold cluster/network execution context of that kind for `apply`-adjacent state). Agents are limited to `terraform init -backend=false`, which resolves module/provider **selection** for `validate` but does not produce a real, apply-usable lock file the way a full `terraform init` against a real backend does.

**State plainly:** T007-T010's authored output has zero `.terraform.lock.hcl` files. This is expected, not a defect a reviewer should flag against the dispatches. `.gitignore` already documents the intent correctly ("NOT ignored, deliberately: `.terraform.lock.hcl` ... a provider *pin* artifact and Constitution IV requires it committed") — and its `.terraform/` ignore pattern is directory-only (trailing slash), so it does not swallow the sibling `.terraform.lock.hcl` file once one exists (confirmed by re-reading the pattern, see Verified-correct).

**Where this actually gets closed:** T011 (the platform bring-up runbook, `runbook-writer`'s own future task) must include, per stage directory, a real `terraform init` step (full, against the real state — not `-backend=false`) executed by the operator on node A per D-000/D-10, followed by a commit of the resulting `.terraform.lock.hcl` back into the public repo (authored on Windows, executed on Linux, per D-000/D-10 — the operator either commits directly from node A or copies the four lock files back to the authoring machine). This doc does not invent a new task ID for that — T011/T012 already exist and are the natural place, but neither has been authored yet, so this is flagged explicitly rather than assumed covered (Follow-ups below).

## D-06 — Namespaces: one shared `orbital-drift` for platform services, `cnpg-system` for the CNPG operator, `orbital-drift-training` for Argo GPU workloads

Nothing in `tasks.md` specifies namespaces for T007-T010. This is decidable rather than a pure operator-input question, because D-000/D-09's `existingSecret` pattern creates a real technical constraint: Kubernetes secrets are namespace-scoped, and MLflow's `backendStore.postgres.existingSecret.name` / `artifactRoot.s3.existingSecret.name` and Airflow's `data.metadataSecretName` all reference a secret **by name only** — no namespace field, because Helm assumes the secret lives in the same namespace as the release consuming it. If CNPG's `Cluster` (which auto-creates its app secret in its own namespace, D-08 below) and SeaweedFS (whose S3 identity secret T007 must pre-create, D-07 below) live in a *different* namespace than MLflow/Airflow, the `existingSecret` pattern breaks unless something copies the secret across namespaces — and nothing in this repo's stack (no `reflector`, no `kubernetes-replicator`) does that; introducing one would be new scope needing operator sign-off, not a Phase 0 default.

**Decided:**

| Namespace | Holds | Rationale |
|---|---|---|
| `orbital-drift` | CNPG `Cluster` CR, SeaweedFS, lakeFS, MLflow, Airflow, Argo controller | One namespace so every `existingSecret` reference resolves with zero cross-namespace machinery — the project name lowercased, already a valid RFC 1123 label, invents nothing new |
| `cnpg-system` | CloudNativePG **operator** only | Convention widely used in CNPG's own docs/quickstarts for the cluster-scoped controller, kept isolated from the app namespace even when there is only one app namespace — **not independently re-verified against the pinned `0.29.0` chart in this session** (no fetch tool available here), flagged as a T007 confirmation item |
| `orbital-drift-training` | Argo Workflow **pods** submitted for GPU training | T010's own task text already implies a distinct namespace ("GPU RBAC + service account **for training namespace**"). D-000/D-03 states the real GPU-isolation control here is RBAC scoping *which namespace* may reference the `nvidia` RuntimeClass — collapsing training pods into `orbital-drift` alongside the Airflow webserver, MLflow UI, etc. would make that RBAC boundary meaningless, since every unrelated pod in the namespace would need individual review instead of the namespace itself being the trust boundary |

**Residual tension, not resolved here:** if a training Workflow step needs to read SeaweedFS/lakeFS credentials directly (mounting the `orbital-drift`-namespace secret from `orbital-drift-training`), the same cross-namespace problem D-06 was designed to avoid resurfaces for this one case. Three ways out — explicitly copy the secret into `orbital-drift-training` via Terraform, have the workflow step call the service over cluster DNS rather than mounting the credential, or fold training pods back into `orbital-drift` and rely purely on ServiceAccount-level (not namespace-level) RBAC — are **not chosen here**; flagged as a T010 follow-up.

## D-07 — Secret NAMES are Terraform variables consumed via `helm_release` `set{}` blocks, never literals inside `infra/helm-values/*.yaml`; CNPG's secret names are derived from a shared `cluster_name`, not separately invented

This formalizes the pattern the task brief asked for explicitly: a consistent rule so T007/T008/T009 don't each invent their own way of naming/wiring the secrets D-08-D-11 identify.

**Decided:**
- `infra/helm-values/*.yaml` files stay static, literal, and fully reviewable — they carry chart configuration that is *not* a secret name (replica counts, resource requests, image settings already pinned elsewhere). They **never** contain a hardcoded secret-name string.
- Every `existingSecret`-shaped value (CNPG's `.spec.bootstrap.initdb.secret.name`, MLflow's `backendStore.postgres.existingSecret.name`/`artifactRoot.s3.existingSecret.name`, SeaweedFS's `s3.auth.existingSecret`, Airflow's `data.metadataSecretName`/`fernetKeySecretName`) is injected from the paired `.tf` file via `helm_release { set { name = "..."; value = var.xxx } }`, sourced from a Terraform variable — never typed into the YAML. This keeps the parameterization boundary exactly where D-000/D-10 already draws it for host-specific values ("sourced from gitignored `.env`/`*.tfvars`"), rather than inventing a second, YAML-side mechanism.
- **CNPG-managed secrets are not given their own name variable.** CNPG's resolved behavior (D-08) is that it auto-creates `<cluster-name>-app` (and, if ever enabled, `<cluster-name>-superuser`) from the `Cluster` resource's own `metadata.name`. Fixing a single shared `var.cnpg_cluster_name` (proposed default: `orbital-drift-postgres`) and letting every consumer build the reference as `"${var.cnpg_cluster_name}-app"` is strictly less error-prone than declaring a second, independently-named secret variable that could drift out of sync with the cluster name itself.
- **SeaweedFS's S3 identity secret has no chart-generated default** (D-10) — someone must pre-create it. `var.seaweedfs_s3_secret_name` (proposed default: `orbital-drift-seaweedfs-s3-credentials`), declared **identically** (same variable name, same default literal) in T007's `seaweedfs.tf` (which creates it), and again in T008's `mlflow.tf` and T009's `airflow.tf` (which only reference it). Separate Terraform root modules (D-01) have no native way to import one another's variables — re-declaring the same name+default in each consuming root is the accepted, standard pattern for loosely-coupled roots that share only a naming convention, not object references.
- **lakeFS's secret is its own, not CNPG's or SeaweedFS's directly** (D-11) — `var.lakefs_secret_name` (proposed default: `orbital-drift-lakefs-secrets`), declared and created in T007's `lakefs.tf`. Whether its `secretKeys.databaseConnectionString` can source CNPG's app secret directly or needs a transformation step is D-11's open question, not resolved here.
- Whether MLflow's own `auth.existingAdminSecret` gets used at all is **not decided here** — see Follow-ups.

## D-08 — CloudNativePG (T007): app-user and superuser secrets are named via CR fields, not chart values, and are auto-created if unset **[RELAYED, NOT INDEPENDENTLY VERIFIED — see Provenance]**

Relayed from the orchestrator's session-time fetch, not independently re-verified here (see Provenance). The Cluster CRD's app-user secret name is set via `.spec.bootstrap.initdb.secret.name`; if unset, CNPG creates `<cluster-name>-app` automatically. The superuser secret is set via `.spec.superuserSecret` (name only); if unset, CNPG creates `<cluster-name>-superuser` automatically, but only takes effect when `.spec.enableSuperuserAccess: true` — `false` has been the hardened default since operator 1.21+, and an app that doesn't need superuser access (nothing in T007-T010's task text asks for one) should leave it off.

Source: https://cloudnative-pg.io/documentation/1.24/applications/ · https://cloudnative-pg.io/documentation/1.15/security/ (retrieved by the orchestrator 2026-08-16; the doc set spans versions 1.15-1.24 in the search results actually returned, not a page pinned to the exact operator `0.29.0`/app `1.30.0` this repo installs). **Residual risk:** the mechanism is stable across every version checked, which is suggestive but not proof it holds at `1.30.0` specifically — flagged as a T007 follow-up to confirm against the version-matched doc page if one can be found, per the original research note's own instruction.

## D-09 — MLflow community chart `1.11.4` (T008): `existingSecret`/`existingDatabaseSecret` key paths for the Postgres backend store and S3 artifact store **[RELAYED, NOT INDEPENDENTLY VERIFIED — see Provenance]** — **CORRECTED 2026-08-16, see D-003/01**

**Correction:** the original relay below claimed `backendStore.postgres.existingSecret.name/.usernameKey/.passwordKey`. **That key path does not exist in the chart.** The T008 dispatch (`infra-scaffolder`) found this while implementing the wiring — its own first `WebFetch` attempts against the tagged `1.11.4` URL gave two different, mutually contradictory answers (an LLM-summarized fetch echoed back the wrong nested shape as if confirmed; a second summarized fetch returned a different, self-contradicting shape), so it fell back to an unmediated `curl` of the raw tagged file and cross-checked the finding against the actual consuming Helm templates (`templates/configmap.yaml`, `templates/deployment.yaml`), not just the values.yaml comments. ## D-12 — `20-platform` provider/variable ownership: one dedicated `providers.tf`, not "whichever `.tf` file happens to land first" — added 2026-08-16, after T008 flagged the gap **[Structural fix, not relayed research]**

D-03 states every stage directory's `versions.tf` is identical across the four *stage directories* and requires no per-file resolution. It does not address a narrower problem specific to `20-platform`: that single stage directory receives **four separate `.tf` files from four separate dispatches** (T007's `lakefs.tf`, T008's `mlflow.tf`, T009's `airflow.tf`, T010's `argo_workflows.tf`), all sharing one Terraform root module and therefore one namespace for `provider {}` and `variable {}` declarations. Terraform allows each exactly once per module — not once per file. Four dispatches each independently declaring `provider "helm" {}`, `provider "kubernetes" {}`, `variable "kubeconfig_path"`, and `variable "orbital_drift_namespace"` (all four genuinely need all four) hard-fails `terraform init`/`validate` with a duplicate-configuration error the moment more than one such file coexists — invisible to any single dispatch validating its own file in isolation, since D-01's per-stage validation command (`cd infra/terraform/<stage> && ...`) only ever sees the files the dispatch itself wrote.

T008 discovered this while implementing `mlflow.tf` (recorded in `docs/decisions/003-t008-mlflow-secret-wiring-findings.md` D-003/04) and, being first to land in its own isolated worktree, declared the shared blocks in `mlflow.tf` itself with a loud request for T007/T009/T010 to reference rather than redeclare them — a reasonable emergency fix, but "whichever dispatch happens to be first-integrated owns the shared declarations" is exactly the kind of accidental, non-discoverable ownership this doc exists to prevent elsewhere (D-03's own provider-pin problem, one level up).

**Decided, at integration time:** `infra/terraform/20-platform/providers.tf` — a fifth file, added to D-01's per-stage file list specifically for `20-platform` (the only stage directory with this multi-dispatch-single-module shape) — holds exactly and only: `provider "kubernetes" {}`, `provider "helm" {}`, `variable "kubeconfig_path" {}`, `variable "orbital_drift_namespace" {}`. Every component file (`lakefs.tf`, `mlflow.tf`, `airflow.tf`, `argo_workflows.tf`) references `var.kubeconfig_path`/`var.orbital_drift_namespace` as already-declared and contains no `provider {}` block of its own. This is the orchestrator's integration-time resolution of the four dispatches' artifacts, not a new agent dispatch — recorded here because it changes D-01's stated file list for `20-platform` specifically and a future reader of D-01 alone would not know about it otherwise.
